# Independent review prompts

Use these prompts in the **private GG QuotaGuard repository**. Run one review with GitHub Copilot's coding agent and one with Claude Code. Give each reviewer a separate branch or checkout, then compare the findings before combining patches. A second reviewer should independently challenge the accounting model rather than simply approve the first reviewer's changes.

Current recorded baseline before independent review: **59 passing tests on Linux; 47 passing and 12 skipped on Windows; nine actual isolated Autobrr external-filter cases passed. GitHub Actions also passed the unprivileged Docker suite and complete/partial bind-mount fixtures.** Check [TESTING.md](TESTING.md) for the current evidence; these figures are a starting point, not a certification. Windows skips must not be counted as Linux coverage.

The intended Autobrr argument template contains only the numeric size macro:

```text
check --config /ABSOLUTE/config.json --size {{ .Size }}
```

The tool generates a fresh opaque reservation ID per attempt. A retry can therefore reserve again, conservatively reducing available capacity. Explicit `--request-id` is for trusted operator/test CLI use; do not interpolate release names, indexer fields, URLs or torrent IDs into it. Reviewers must test random-ID generation failure and duplicate-option rejection as well as reservation accounting.

## Prompt for GitHub Copilot coding agent

Copy the following into a Copilot agent task in the private repository:

```text
Independently review and adversarially test GG QuotaGuard before its owner decides whether to make the repository public.

Keep this repository PRIVATE. Do not publish a release, change repository visibility, submit upstream contributions, send community messages, deploy anything, or contact external services with project data. Work on a separate review branch. Do not access production credentials, real downloads, live Autobrr filters/configuration, provider-managed services, or another user's files. Test with synthetic files and isolated state only. Do not use root, privileged containers, host Docker sockets inside containers, or provider infrastructure changes.

First read README.md, gg_quotaguard.py, docs/SAFETY.md, docs/RESEARCH.md, docs/TESTING.md, tests/, and the testing matrix in docs/REVIEW-PROMPTS.md. Identify the trust boundaries and the exact conditions under which exit 0 is safe. Record the starting commit and environment.

Your main job is to find reproducible unsafe acceptances, incorrect accounting, incomplete fail-closed behavior, integration errors, or misleading safety claims. Passing existing tests is not enough. Build an independent oracle from explicit byte budgets and externally observed reservations; do not copy the implementation's formulas or mocks into tests and call that independent validation. Challenge assumptions about quota scope, untracked downloads, filesystem visibility, ledger integrity, and external writers.

Run the full existing suite and syntax checks. Then exercise every applicable item in the testing matrix. Use real separate processes for ledger concurrency/crash tests, and real Linux filesystem operations for permission, sparse-file, hardlink and symlink behavior. Exercise Python 3.9 and 3.13 and the unprivileged Docker fixtures where the environment supports them. If a version or Docker is unavailable or daemon access is denied, record NOT RUN with the precise reason; do not substitute mocks and mark it passed. Do not change provider permissions to enable testing.

Before fixing a suspected defect, save a minimal synthetic counterexample showing the observed result, independently expected result, exit status, and why they differ. Add a regression test that fails on the starting implementation, then make the smallest justified patch and rerun the affected and full suites. Do not change acceptance rules merely to make tests pass. Treat uncertain measurements as rejection, and avoid automatic reservation expiry or release.

Bound your work to 60 minutes or 20 investigation iterations. Run at most 16 worker processes; keep synthetic allocated data below 256 MiB and ordinary scan fixtures below 10,000 entries. Use explicit process timeouts and terminate only your own test processes. Large logical sizes should use sparse fixtures or numeric inputs. Save an honest checkpoint if a limit is reached. Do not fill a real filesystem or change its quotas.

Deliver a review report with: starting/final commit; environment and commands; tests passed/failed/skipped/not run; prioritized findings with file/line references and minimal reproductions; independent oracle and invariants; patches and regression evidence; limitations that remain; and a recommendation of DO NOT PUBLISH, READY FOR OWNER REVIEW, or INSUFFICIENT EVIDENCE. READY FOR OWNER REVIEW does not authorize publication or imply absolute safety. Separate implementation bugs from documented operating assumptions and from unverified HBD Docker compatibility.

If the agent workflow automatically opens a draft pull request inside this private repository, keep it private and unmerged. Do not open any pull request against autobrr/community-scripts or any other repository.
```

## Adversarial testing matrix

For every case, record the observed exit status, parsed JSON decision, elapsed time, and ledger change. A test that raises an unrelated exception is not evidence that the intended safety condition was handled. A process timeout must be detected as failure, and missing output must never be interpreted as acceptance.

| Area | Required experiments and independent checks |
| --- | --- |
| Acceptance invariant | Use small, explicit byte budgets with independently calculated expected decisions. Include equality, one byte below/above the threshold, existing pending reservations, near-full capacity, and zero available capacity. For any successful check, show the matching durable reservation exists after a fresh process reopens the database. |
| Incoming size | Test absent, zero, negative, fractional, scientific notation, whitespace, Unicode digits, units, huge integers, signed values, and values at supported integer boundaries. Unknown size must reject. Test numeric overflow in the combined pending/incoming/reserve values. Distinguish torrent logical bytes from eventual filesystem overhead and verify the documentation states the buffer's limits. |
| Configuration | Test invalid JSON, duplicate JSON keys, unknown keys, incorrect types, boolean-as-integer values, zero/negative buffers, missing confirmations, incorrect manual quotas, relative/noncanonical paths, and configuration changes after ledger initialization. Verify examples reject until explicitly configured. A manual quota cannot be inferred to be correct merely because a test passes. |
| Quota output | Use unscaled quota-tools output, supported numeric grace fields, stars only in permitted positions, zero/unlimited limits, soft/hard disagreement, exhausted inode limits, multiple devices, duplicate target rows, missing target rows, wrapped or truncated rows, human-readable units, localized output, warnings on stderr, nonzero exit codes and empty output. Preserve malformed raw fixtures without account information. Invalid or ambiguous output must reject without falling back to host free space. |
| Quota scope | Verify the target device matches the quota device, including a bind-mounted source suffix. Test mismatches and changed mount sources. Explain how stricter group/project/provider quotas, remote storage policies, or unavailable quota enforcement could invalidate a user-quota report. Require verified scope; an unknown effective limit is not established capacity. Do not claim every effective quota can be discovered automatically. |
| Filesystem cap | Make the account quota roomier than filesystem capacity, then the reverse. The lower usable capacity must constrain acceptance. Cover read-only targets, missing/unwritable paths, unavailable statvfs, inode exhaustion and malformed/unavailable source discovery. Never approve using filesystem free space alone. |
| Ledger integrity | Start with missing, empty, corrupt, truncated, read-only, locked, symlinked or wrongly permissioned state. Modify otherwise valid SQLite rows to contain text/real/zero/negative/out-of-range amounts, invalid IDs, invalid timestamps, bad metadata, or an overflowing aggregate. Bypass CHECK constraints only in disposable corrupted-state fixtures. Unknown state must reject without recreating an empty ledger. |
| Transactions and crashes | With real independent processes, kill a test process before commit, after database insertion but before commit, and after commit but before output where reproducibly observable. Check the ledger from a fresh connection. A reported acceptance must have committed state; an ambiguous interrupted attempt may remain conservatively reserved. Inject commit/storage errors and assert no acceptance is emitted. |
| Concurrent admission | Use a barrier to start independent processes sharing one ledger. Give them a fixed small capacity allowing a known maximum number of accepted releases. Vary sizes and schedules; assert accepted bytes plus the reserve never exceed the independent budget. Include lock contention, duplicate IDs, different IDs, process restarts and changed configuration. Separate ledgers for one pool are a misconfiguration; tests must not silently use separate state per worker. |
| Reservation lifetime | Verify restart and elapsed time do not expire reservations. Default attempts must receive fresh generated IDs; random-ID generation failure must reject. With trusted operator-supplied IDs, repeated IDs reject conservatively; fresh IDs may consume more reservations. Test explicit release acknowledgement, missing/nonexistent hashes and measured-state failure during release. Review why premature manual release, untracked startup downloads or an external downloader can defeat otherwise correct admission accounting. |
| Directory traversal | Use real hidden files/directories, empty directories, multiple and overlapping roots, hardlinks across roots, sparse and preallocated files, inaccessible paths, missing entries, symbolic links and special files. Compare accounting with an independently enumerated inode set and allocated/logical sizes. No silent omission of inaccessible data or accidental double deduction is acceptable. Check that the download target is inside the measured scope and cross-filesystem paths reject. |
| Directory races | Create, remove, rename, replace, grow and truncate synthetic files during a scan. Test the documented race detection and bounded retry/rejection behavior. Specifically inspect replacement of a directory with a symlink between metadata inspection and enumeration. Do not claim ordinary traversal is an atomic filesystem snapshot or immune to all external writers. |
| Incomplete visibility | Run complete-view and partial-view bind-mount fixtures. Missing configured scope must reject. Also demonstrate the limitation of an omitted, unconfigured billed directory: the program cannot discover storage hidden from its namespace. Include deleted-but-open synthetic files and same-filesystem overmount/alias scenarios when facilities permit. Record unavailable mount facilities as NOT RUN; never claim automatic coverage detection from these fixtures. |
| Resources and deadlines | Check entry and time budgets during enumeration, not only after a huge directory has been queued. Test command timeouts, slow/no-output helpers, filesystem errors, lock timeout and process cleanup. Measure peak memory and elapsed time with bounded synthetic workloads. Do not stress a shared provider, fill a filesystem, or repeatedly scan real media. |
| Autobrr execution | Confirm the actual supported external-filter exit/status model and minimum-size setting from upstream source/docs. Verify the documented template uses only `{{ .Size }}`, a numeric macro, and no dynamic string macros. Exercise real argv construction where possible: macros are expanded before shell-style argument splitting; lack of a shell does not itself prevent argument injection. Test quotes, newlines, duplicate option names and flag-like input in direct CLI attempts, including `--option=value` forms. Duplicate size/config/request-ID options must reject, not silently override. Verify untrusted macro content cannot replace size/config/state arguments, and show why adding string macros would reintroduce risk. Do not put credentials or private release names into command arguments. |
| Privacy and failures | Trigger permission errors, parser failures, exceptions and timeouts with synthetic paths and canary secrets. Verify normal JSON and error output do not expose raw request IDs, usernames, private paths, passkeys, tokens or raw storage command output. Check that tests and generated reports also omit secrets. Require nonzero rejection on failure, one expected JSON result where applicable, and no false pass from missing output. |
| Environment fidelity | Run supported Python versions on Linux. Run containers as an unprivileged UID with dropped capabilities, no-new-privileges, read-only root and bounded temporary storage. Test bind mounts and host/container view differences without exposing the Docker socket or real download paths. Label mocks, real filesystem experiments, real kernel quota observations and actual Autobrr integration separately. |

## Evidence needed before a public-release decision

Reviewers should supply reproducible findings and a complete matrix of passed, failed, skipped, and not-run cases. Keep raw account evidence outside the repository; publish only sanitized synthetic fixtures and aggregate results. Resolve unsafe acceptance defects before considering visibility changes, and clearly document remaining deployment assumptions.

Neither reviewer should turn the repository public. No finite test suite proves absolute safety, and a successful isolated user-space deployment does not establish compatibility with HostingByDesign's managed Docker environment. The owner makes the publication decision after reviewing the independent reports.
